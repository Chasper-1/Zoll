# Движок-парсер Zoll: как он устроен

> Документ описывает то, как парсер устроен **сейчас** (реализация в `src/engine/`).
> Пункты, которые остаются спецификацией и ещё не реализованы, помечены **(спека)**.

## Обзор

Парсер не строит токены и деревья. Он находит маркеры в тексте и выдаёт список синтаксических диапазонов — у каждого диапазона есть начало, конец и тип (жирный, заголовок, комментарий и т.д.). Всё в абсолютных байтовых координатах. Всё остальное (рендер, редактор) работает поверх этих диапазонов.

Пайплайн — два прохода:

```
текст документа
    ↓
проход 1: поиск переводов строк → карта строк
    ↓
проход 2: поиск маркерных символов → объединение в маркеры → классификация
    ↓
диапазоны + позиции переводов строк
```

## Модули

| Файл | Роль |
|---|---|
| `parser.rs` | Публичный интерфейс движка и сам пайплайн из двух проходов |
| `simd.rs` | Быстрый поиск значимых символов |
| `resolver.rs` | Классификация маркеров: превращает маркеры в диапазоны |
| `line_map.rs` | Карта строк: позиции переводов строк |
| `dependency.rs` | Граф зависимостей диапазонов |
| `api.rs` | Ручки — контракт между движком и редактором |

## Проход 1: карта строк

Один проход ищет только переводы строк и запоминает их позиции. Никакой логики языка. По карте можно мгновенно узнать номер строки по байтовой позиции и границы любой строки.

## Проход 2: маркеры

Второй проход ищет все синтаксически значимые символы. Для каждого найденного символа:

1. **Объединение в маркер.** Подряд идущие одинаковые символы сливаются в один маркер. Например, две звёздочки подряд — это один маркер жирного, а не две отдельные звёздочки: быстрый поиск умеет находить только одиночные символы, а склейку делает этот этап.
2. **Перевод строки.** Строка кончилась — границы новой строки берутся из готовой карты (сканировать текст заново не нужно). Открытые inline-маркеры сбрасываются: они не выходят за пределы строки. Строчные маркеры без закрытия действуют до конца строки. Блочные маркеры переживают строки.
3. **Классификация.** Завершённый маркер передаётся классификатору.

## Классификация маркеров

Классификатор — тонкий диспетчер по символу:

| Символ | Что делает |
|---|---|
| Пара закрывающих скобок `))` | Закрывает **все** открытые inline-маркеры разом |
| Закрывающая скобка `}` | В начале строки — закрывает блок; в середине строки — закрывает строчный маркер |
| Точка `.` | Проверяет нумерованный список (`1. ` в начале строки) |
| Остальное | Открытие маркера: блок → строчный → структурный → inline |

Уровни маркеров (см. `docs/syntax.md`, раздел 9):

- **Inline:** `**` `//` `__` `~~` `==` `++` `--` `''` `,,` `$` `%` `!` — в любом месте строки, закрываются `))`. Открытые маркеры лежат в стеке; `))` закрывает все разом.
- **Line (close):** `%%` `$$` `!!` `>` — только в начале строки, закрываются `}` (приоритетнее) или действуют до конца строки автоматически.
- **Line (not-close):** `#1` `#:` `-` `1.` `---` `|` — только в начале строки, диапазон сразу до конца строки.
- **Block:** `%%%` `$$$` `!!!` `@@` — только в начале строки, переживают строки, закрываются `}` в начале строки.

Правила пробелов: после открывающего маркера и перед закрывающим пробел запрещён. Незакрытые inline-маркеры выбрасываются; незакрытые строчные действуют до конца строки; незакрытый блок в конце документа выбрасывается.

## Поиск символов (SIMD)

Первый этап отвечает исключительно за быстрый поиск синтаксически значимых символов. Он не определяет, что найденный символ означает, не строит маркеры и не занимается грамматикой.

Документ последовательно разбивается на блоки по 16/32 байта. Для каждого блока загружается регистр и выполняется поиск интересующих символов.

Результатом обработки блока являются:

`регистр + битовая маска + абсолютное смещение блока`

Битовая маска имеет размер регистра. Если бит равен 1, соответствующий байт в регистре является найденным.

Например:

```
register:
[ a b c } d e * f g h i j ) ... ]
mask:   1     1           1
        ↑     ↑           ↑
0       3     6           12
```

Маска не хранит тип найденного символа — она только указывает его положение внутри регистра. Сам байт берётся из регистра по этой позиции.

Если начало блока находится на позиции 4096, результат преобразуется в:

```
position  byte
4100      }
4103      *
4108      )
```

Таким образом, первый этап передаёт дальше поток событий вида «позиция + символ». Сам слой поиска ничего не знает о синтаксисе Zoll: для него существует только понятие «интересующий символ». Что означает последовательность найденных символов (например, `))`, `}`, `**`) — решает следующий уровень.

Главная задача этого этапа — одним проходом по большим блокам данных быстро получить координаты всех потенциально значимых символов, не заставляя основной парсер сканировать весь текст повторно.

**Два способа поиска:**

1. **Табличный** — основной путь. Вместо сравнения с каждым целевым символом заранее строится пара таблиц, и каждый байт классифицируется по своим двум половинкам за пару подстановок. Точный, без ложных срабатываний. Требует поддержки архитектурой (SSSE3/AVX2 на x86, NEON на ARM).
2. **Сравнение** — запасной путь для архитектур без табличной поддержки и для наборов целей со старшими байтами.

Выбор пути — на каждом вызове: AVX2 → SSSE3 → SSE2 → NEON → скаляр, с учётом доступности таблиц.

## Движок и ручки

Движок хранит состояние документа: текст, номер версии, карту строк, диапазоны и граф зависимостей.

- **Полный разбор** — документ разбирается с нуля, версия 0.
- **Правка** — применяется к буферу, номер версии увеличивается на 1, документ переразбирается целиком. Инкрементальный переразбор только затронутых блоков — следующий шаг **(спека)**.
- **Отправка результатов** — «выстрелил и забыл»: движок передаёт диапазоны по ручке и не ждёт ответа. Спаны уходят **по мере готовности**: каждый спан отдаётся в момент, когда он полностью определён (inline — при закрытии `))`, строчные — при `}` или в конце строки, блочные — при закрытии `}`). Редактор получает первые спаны, не дожидаясь конца парсинга. Пачка вызовов между `begin_revision` и `end_revision` — одна версия документа.
- **Ручка движка** — единственный объект, который держит редактор: разбор, версия, диапазоны, номер строки по позиции, запросы диапазонов по области, применение правок.

Правка описывается как изменение байтового буфера: удалить кусок `[позиция, позиция + длина)` и вставить новый текст. Дополнительно считается изменение длины документа.

Граф зависимостей — диапазоны, отсортированные по позиции. Два запроса: диапазоны, полностью лежащие в области, и диапазоны, пересекающие область.

## Координатная система

Всё в абсолютных байтовых позициях: диапазоны, правки, карта строк. Никаких юникод-символов, строк и деревьев. Редактор получает исходный буфер и диапазоны в байтовых координатах.

## Блоки метаданных

Метаданные документа (`@@ ... }`) — единственное исключение из общего правила: основной парсер **не разбирает содержимое** блока. Он распознаёт границы блока по общим правилам (открытие `@@` в начале строки, закрытие `}` в начале строки) и передаёт дальше один диапазон на весь регион.

Разбор содержимого (`title`, `author` и прочие поля) выполняется **отдельным проходом вне основного конвейера**. В редакторе это отдельный поток: основной парсер указывает ему границы региона — «вот здесь работай» — и не ждёт результата. Это соответствует принципу асинхронности: основной парсер не блокируется содержимым метаданных и не знает их формат. **(спека: сам проход ещё не реализован — парсер пока только помечает регион)**

## Текущие ограничения

- Правка пересобирает весь документ; инкрементальный переразбор затронутых блоков — следующий шаг.
- Второй проход (грамматика) однопоточный; параллельная обработка блоков — **(спека)**.
- Содержимое метаданных `@@` ещё не разбирается отдельным проходом (парсер помечает только регион — см. раздел «Блоки метаданных»).
- Ещё не реализовано: таблицы с выравниванием, экранирование `\`, инлайн-код, парные скобки (ссылки/термины/макросы), callout-блоки.
